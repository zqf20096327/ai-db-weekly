# 落地实施方案：site-demo → 正式站点

> 目标：把 demo 的四入口结构（周报 / 往期 / 月度速报 / 生态地图）落成正式静态站，
> 数据由 `D:\daily_github\v2` 的日快照管道驱动，**每天采集后分钟级完成聚合更新**。
> 本方案同时是施工任务书：每个里程碑列出要写的文件和验收标准。

## 一、总体架构

```
D:\daily_github\v2（采集与聚合侧）                D:\db-oss-observer\blog-site（站点侧）
┌─────────────────────────────┐                 ┌──────────────────────────────┐
│ run_daily.py（已有，每天）      │                 │ index.html + assets/app.js     │
│   └→ data/snapshot_YYYYMMDD/  │                 │  （重构为 demo 的路由结构）      │
│                              │    JSON 文件      │  #/weekly #/past #/monthly     │
│ site_export/（新增包）         │ ───────────────→ │  #/map（矩阵+档案双视图）        │
│  history.json  ← 增量追加      │  data/site/*.json│  #/archive/{db}                │
│  aggregate_daily.py（每天）    │                 │                                │
│  export_weekly.py（每周）      │                 │ data/site/*.json（no-cache）    │
│  aggregate_monthly.py（每月）  │                 │ data/issues/…（旧两期兼容）      │
└─────────────────────────────┘                 └──────────────────────────────┘
        deploy.sh（已有：校验 + 上传 index/assets/data）→ Nginx
```

原则：**聚合代码放 v2**（复用 filters/sections/analytics 同一套口径），站点只消费 JSON；
blog 的 `build_index.py` 继续做上线前校验（schema 检查后述）。

## 二、关键设计：history store（快的前提）

**不要每次聚合都重读 47 个快照/zip。** 维护一个紧凑的增量历史库
`v2/site_export/history.json`：

```json
{
  "watched": {                        // star≥10 ∪ 历史上榜 ∪ 解读对象（已定，约 5k 项目）
    "t8y2/dbx": {
      "first_seen": "20260815",
      "anchors": {"20260818": 15521, "20260826": 16310, "…每周锚点": 0},
      "daily": {"20260915": 19509, "20260916": 19689},   // 仅 watched 存日序列，供 sparkline
      "last_stars": 20252
    }
  },
  "pool_seen": {"项目名": "最后出现日", "…全池 1.6 万项只记出现日，不存数值"},
  "meta": {"updated": "20260921", "anchor_rule": "每周最后一个快照日"}
}
```

- **每日更新** = 读当日 `merged/all_projects.json` 一遍（16k 项，1-2 秒）：
  watched 项目追加日序列；池项目刷新 last_seen；跨周时落一个锚点；
- **周/月聚合只读 history**（几十 KB），不碰快照——这就是「快速更新」的来源；
- **一次性迁移**：写 `backfill.py` 把 39 个 zip + 27 个目录里的锚点/日序列灌进去（约 1 分钟，只跑一次）；
- 防呆：日期参数必须 `^\d{8}$`（本次踩过的 `snapshot_snapshot_` 垃圾目录教训），启动时自检。

体积账：watched ≈ 4.9k 项（star≥10，实测 2026-09-21 池：国产板块 148 / 国际+AI 4772）
× 每日 1 个数值，年增约 20MB，日聚合仍是秒级，完全可控。

**watched 边界（已定）：star≥10 ∪ 历史上榜 ∪ 历史解读对象。**
数据层不做取舍——展示门槛是纯渲染选项（见「输出文件契约」）。
注意：国产判定必须用管道 `sections.assign_section`（token 防误命中），
不得用关键词子串匹配（'admin' 含 'dm' 会被误判达梦，实测踩过）。

## 三、四条流水线

### 1）每日（采集后自动，分钟级）
```
run_daily.py（已有）
  → python -m site_export.aggregate_daily --date 20260922
      ① 更新 history.json（增量追加）
      ② 重生成 data/site/map.json + archive.json（从当日池算，805 项 <1s）
      ③ 重生成 data/site/now.json（更新时间、池规模、KPI）
  → （可选）bash tools/deploy.sh   # 几百 KB JSON，秒级上传
```
耗时：聚合 <5 秒；是否每日部署可选（周四是硬需求，日更是加分项）。

### 2）每周四（出刊）
```
run_weekly.py 全流程（已有：compute→readme→select→ai→render）
  → python -m site_export.export_weekly --date YYYYMMDD
      ① sections + ai_reviews + history 轮换数据 → weekly-{N}.json
         （字段 = demo 契约：kpi / hooks / board_secs / focus+三维 / newfaces /
            topboard / rotated_out；hooks 留空数组时前端显示「待补」占位）
      ② issues-index.json 追加本期（往期页数据）
      ③ 上榜项目自动并入 watched 集合
  → 人工：写 3 条看点（编辑 hooks[3].text）→ 复核 9 项 → deploy.sh
```
**hooks 是全流程唯一人工输入**：导出器生成的 hooks 是占位（数字+项目名），
人工只需改写文案，前端对空 hooks 显示骨架占位，不会出现坏页面。

### 3）每月 1 日
```
python -m site_export.aggregate_monthly --month 2026-09
  从 history 锚点算月窗（最近可用基准对）→ monthly-2026-09.json
  （top_gain / streaks / orgs / month_new，org 对比读首末两天的 orgs/*.json）
```

### 4）灾备重建（罕见）
`backfill.py --full`：从全部 zip+目录重建 history → 重跑三个聚合器。约 2 分钟。

## 四、输出文件契约（v2 → blog-site/data/site/）

| 文件 | 生成频率 | 内容 | 大小参考 |
|---|---|---|---|
| `now.json` | 日 | 更新时间、池规模、KPI、期号 | <1KB |
| `map.json` | 日 | 矩阵计数 + 各库工具列表（全量 ≥10 数据，前端默认分层展示：国际 ≥300 / 国产 ≥50，提供「显示更多（≥10）」切换——数据层不丢，展示层防噪） | ~1MB，超限后按库拆分 |
| `weekly-{N}.json` | 周 | v4 周报全字段（含 spark/三维/轮换） | ~30KB |
| `issues-index.json` | 周 | 往期页清单（期号/日期/看点/状态） | <5KB |
| `monthly-{YYYY-MM}.json` | 月 | 月度速报全字段 | ~20KB |
| `personas.json` | 一次性+增量 | 批量 AI 分类结果（805 项起步） | ~50KB |

拆分策略：`map.json` 超 1MB 后拆成 `map-matrix.json` + `archive-{db}.json` 每库一文件（前端按需 fetch，档案页只拉一个库）。

`build_index.py` 增加校验：JSON 可解析、weekly 必填字段齐全（hooks/board_secs/focus）、
日期为 YYYY-MM-DD——沿用「坏数据不上线」的现有闸门。

## 五、前端落地（blog-site 改造）

1. `index.html + assets/app.js + assets/style.css` 重构为 demo 的路由结构
   （weekly/past/monthly/map 双视图/archive），fetch `data/site/*.json`（no-cache 已配好）；
2. **旧两期迁移**：写一次性转换脚本把 `data/issues/weekly-{1,2}.json` 转成新
   `weekly-{1,2}.json` 格式，统一渲染器，删旧 active_top3 渲染分支；
3. 兼容保留：`#/issue/weekly-N` 旧路由 301 到新路由（外链不断）；
4. 交互照搬 demo：人群页签、格子下钻、档案分组、明暗模式。

## 六、里程碑（按依赖排序）

| 阶段 | 内容 | 工作量 | 验收 |
|---|---|---|---|
| **M1 历史库+日更** | history.json + backfill + aggregate_daily + now/map 输出 | 1-2 天 | 跑一次日聚合 <10s；zip 锚点齐 |
| **M2 前端落地** | app.js 路由重构 + 旧两期迁移 + fetch 化 | 1-2 天 | 本地 server 打开 = demo 效果；旧路由可跳转 |
| **M3 周报导出** | export_weekly + issues-index + hooks 占位机制 | 1 天 | 第 3 期由管道全量产出（除看点文案） |
| **M4 月度聚合** | aggregate_monthly | 0.5 天 | 9 月刊由管道产出 |
| **M5 字段增强** | releases 接回 / GHSA / contributors / personas 批量 AI（对象 = watched 全集 ≈5k，见《数据提取清单》L1/L2） | 按需 | 页面字段逐步长出，不动结构 |
| **M6 自动化** | Windows 计划任务串联 日采集→聚合→（可选）部署；RSS 生成 | 0.5 天 | 无人值守跑一周无人工 |

## 七、决策点（已拍板两项）

1. ~~日更部署 or 周更部署~~ → **已定：日更**。计划任务串联「采集 → 聚合 → deploy.sh」，周四出刊日另行人工复核后部署；
2. ~~watched 集合边界~~ → **已定：star≥10 ∪ 历史上榜 ∪ 解读对象**。展示层默认分层（国际 ≥300 / 国产 ≥50）+ 「显示更多」切换，属渲染选项可随时调；
3. **批量 AI 分类何时跑**：M5，跑完前地图「其他」按现状展示（51%）；
4. **月度 org 对比基准**：自然月 vs 滚动 30 天——建议滚动窗口（跟周报窗口口径一致），页头标注窗口即可。

## 八、风险与对策

- 快照缺口（如 08-07）：锚点跳过机制已内建，口径页声明即可；
- history.json 损坏：每日聚合成功后先写 `history.json.tmp` 再原子替换；保留近 7 份轮转备份；
- v2 与 blog 两仓同步：export 直接写 blog 路径（配置项 BLOG_DATA_DIR），deploy 前跑 build_index.py 校验，失败阻断上传（沿用现有机制）。
