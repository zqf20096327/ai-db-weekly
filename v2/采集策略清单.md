## 第二步：巨型/中型 topic 采集（三层拆分）

**适用**：database / mysql / postgresql / oracle / mariadb / sqlserver（total_count > 1000 的）

**核心思想**：互斥去重 → star≥10 砍噪音 → star 档位拆分规避 1000 上限

> ⚠️ **互斥仅限四大库**：database/mysql/postgresql/oracle。国产库 topic（polardb/opengauss/dm/tidb/oceanbase）**不做互斥**（量小直接全采，且打上游标签会被误杀）。mariadb/sqlserver 不互斥，仅按 star 档位拆。

### 第①层：互斥去重（仅四大库）

**语法**：用减号 `-topic:xxx`（GitHub 不支持 SQL 的 `NOT`，会返回 422）

**互斥规则**：四个"泛库"topic 互相排除，避免同一项目被多个 topic 重复采集。

```
database  互斥 = topic:database  -topic:mysql  -topic:postgresql -topic:oracle
mysql     互斥 = topic:mysql     -topic:database -topic:postgresql -topic:oracle
postgresql互斥 = topic:postgresql -topic:database -topic:mysql  -topic:oracle
oracle    互斥 = topic:oracle    -topic:database -topic:mysql  -topic:postgresql
```

**实测结果**：

| 互斥集 | 互斥后 total_count | 去掉的重叠 |
|---|---:|---|
| database 互斥 | 37,051 | 12,375 |
| mysql 互斥 | 91,429 | 10,692 |
| postgresql 互斥 | 97,828 | 8,072 |
| oracle 互斥 | 4,311 | 1,333 |
| 合计 | 230,619 | 去重 12.3% |

**注意**：mariadb / sqlserver 不参与四库互斥（它们量级小，单独处理）。

### 第②层：star≥10 砍噪音

互斥后仍有几万条，其中 star<10 占 90%+ 是噪音（玩具/作业/废弃）。这些本就要被黑名单过滤，**在采集时就挡掉，省 90% 调用量**。

```
在互斥查询后追加： stars:>=10
```

**实测结果**：

| 互斥集 + star≥10 | 条数 | 变化 |
|---|---:|---|
| database 互斥+star≥10 | 5,425 | 从 37k 砍到 5k |
| mysql 互斥+star≥10 | 4,909 | 从 91k 砍到 5k |
| postgresql 互斥+star≥10 | 4,590 | 从 98k 砍到 5k |
| oracle 互斥+star≥10 | 405 | ✓ 一次采完 |

> ⚠️ **为什么 star≥10 而不是更高**：周报的②新生项目榜口径是 star≥3，需要覆盖早期项目。star≥10 是"快照全量采集"的下限，新生项目榜另有独立的 30 天窗采集（第五步），下限 star≥3。

### 第③层：star 三档拆分（解决 1000 条硬上限）

star≥10 后仍有 4000-5000 条 > 1000 上限，按 star 档位拆：

```
对每个互斥集 + star≥10 的部分，拆三个子查询：

子查询1： {互斥集} stars:>=10 stars:10..99      ← 实测 3000-4000，仍超1000，需第④层
子查询2： {互斥集} stars:>=10 stars:100..999    ← 实测 700-1200，基本可采
子查询3： {互斥集} stars:>=10 stars:>=1000      ← 实测 100-400，可采
```

**实测（以 mysql 为例）**：

| 子查询 | 条数 | 是否超1000 |
|---|---:|---|
| mysql互斥+star10-99 | 3,918 | ⚠️ 超，需第④层 |
| mysql互斥+star100-999 | 802 | ✓ 可采 |
| mysql互斥+star≥1000 | 189 | ✓ 可采 |

### 第④层：star10-99 按 created 日期拆（仅此档需要）

star10-99 仍有 3000+ 超 1000 上限，按创建日期拆成多段：

```
对 star10-99 的部分，按 created_at 年份拆：

{互斥集} stars:10..99 created:>=2025-01-01          ← 今年
{互斥集} stars:10..99 created:2024-01-01..2024-12-31 ← 去年
{互斥集} stars:10..99 created:2023-01-01..2023-12-31 ← 前年
{互斥集} stars:10..99 created:<=2022-12-31           ← 更早
```

> 📌 **动态拆分原则**：脚本检测每段的 total_count，若某段仍 > 1000，继续按半年/季度拆，直到每段 ≤ 1000。

### 完整查询语句示例（以 mysql 为例）

```
# ① 互斥 + star≥100（一次采完）
q=topic:mysql -topic:database -topic:postgresql -topic:oracle stars:>=100
# total_count ≈ 991，分页 10 页采完

# ② 互斥 + star10-99 + 按日期拆
q=topic:mysql -topic:database -topic:postgresql -topic:oracle stars:10..99 created:>=2025-01-01
q=topic:mysql -topic:database -topic:postgresql -topic:oracle stars:10..99 created:2024-01-01..2024-12-31
q=topic:mysql -topic:database -topic:postgresql -topic:oracle stars:10..99 created:2023-01-01..2023-12-31
q=topic:mysql -topic:database -topic:postgresql -topic:oracle stars:10..99 created:<=2022-12-31
# 每段约 800-1200，分页采完
```

### mariadb / sqlserver 的处理

这两个中型 topic（5k 左右）不参与四库互斥，但同样用 star 档位拆分：

```
# mariadb
q=topic:mariadb stars:>=100              ← 约 200 条，一次采完
q=topic:mariadb stars:10..99 created:>=2025-01-01
q=topic:mariadb stars:10..99 created:<=2024-12-31

# sqlserver（同理）
q=topic:sqlserver stars:>=100
q=topic:sqlserver stars:10..99 created:>=2025-01-01
q=topic:sqlserver stars:10..99 created:<=2024-12-31
```

## 第四步半：Org 全量扫描（补 topic 搜索盲区）

**目的**：实测发现多个内核 repo 的 topics 为空（mysql-server、openGauss-server），topic 搜索完全搜不到。必须扫描官方 org 下的全部 repo 来补采。

### 查询方式

```
对每个 org：
GET /orgs/{org}/repos?sort=stars&direction=desc&per_page=100&type=public
（走 Core API 5000/小时配额，不占 Search 限流）
```

### Org 扫描清单

```
mysql              ← mysql/mysql-server 等 24 个（topics 为空的内核在此）
polardb            ← PolarDB 全家桶（topic:polardb 只有4个，org 补全）
ApsaraDB           ← 阿里云数据库工具生态
oceanbase          ← OceanBase 内核 + 工具
opengauss-mirror   ← openGauss 系（topics 为空，靠 org）
pingcap            ← TiDB 生态
tikv               ← TiKV 生态
```

### 为什么需要这步（实测证据）

```
mysql/mysql-server 的 topics = []（空）  → topic 搜索搜不到
opengauss-mirror/openGauss-server 的 topics = []（空）→ topic 搜索搜不到
polardb/PolarDB-for-PostgreSQL 的 topics 含 database+postgresql，
  但无 polardb → topic:polardb 搜不到，且互斥 -topic:database 会误杀

→ 这些都靠 org 扫描兜底
```

### 调用成本

```
mysql org: 24 个 repo → 1 次调用（per_page=100 一次取完）
polardb org: 小 → 1 次
共 7 个 org → 约 7 次调用（Core API，不占 Search 限流）
```

## 全局规范：限流/错误/落盘/去重

### 限流处理（核心！）

```python
# 每次调用后读取响应头
remaining = response.headers.get("X-RateLimit-Remaining")
reset_ts  = response.headers.get("X-RateLimit-Reset")

if int(remaining) <= 5:
    # 等到重置时间
    wait = int(reset_ts) - int(time.time()) + 2
    if wait > 0:
        time.sleep(wait)
else:
    time.sleep(2)  # 正常间隔 2 秒

# ❌ 绝对不要固定 sleep(61)，会导致总耗时 = 调用数 × 61 秒
```

### GitHub Search 1000 条硬限制处理

```python
total_count = response["total_count"]
if total_count > 1000:
    # 不能直接采，必须拆分查询（star档位 / created日期）
    # 脚本自动触发拆分逻辑
    trigger_sub_split(query, total_count)
else:
    # 可采，分页 per_page=100，最多 total_count/100 页
    fetch_all_pages(query)
```

### 错误处理

```python
HTTP 403 → 限流，读 X-RateLimit-Reset，等到重置后重试
HTTP 422 → 查询语法错误（如用了 NOT topic:），改用减号语法
HTTP 404 → repo 不存在/已删除，记录跳过
HTTP 5xx → GitHub 服务端错误，等 10 秒重试，最多 3 次
超时     → 30 秒超时，重试 1 次
```

### 落盘规范

```
① 每次查询结果立即写入文件，不要等全部跑完再写（防中断丢数据）
② 文件命名：data/snapshot_{date}/topics/{topic}.json
③ 写入格式：JSON Lines（每行一个项目）或 JSON 数组
④ 采完一个 topic 就 flush 到磁盘
⑤ 脚本支持断点续采：读取已有文件，跳过已采的 topic
```

### 去重规范

```
① 跨 topic 去重：按 full_name 去重（同一项目被多个 topic 采到）
② 白名单优先：与白名单合并时，白名单为准
③ fork 去重：fork=true 的默认剔除（除非 star 远超原项目）
④ 合并后写入：data/snapshot_{date}/merged/all_projects.json
```
