性能标尺的更新周：ClickBench 一周 618 次提交

ClickHouse/ClickBench

分析型数据库的公共基准测试套件——上百引擎同场竞技的结果页，本周 7 天 618 次提交、90 天 5,143 次，维护强度罕见地高。

1.2k Star+6 本周618 c/7天144 贡献者
阅读全文 ↓

ClickBench 是面向分析型数据库的可复现基准测试套件：同一套查询、统一口径、上百种引擎的结果大表，是 OLAP 选型圈被引用最多的「公共标尺」之一。仓库由 ClickHouse 官方维护（2022 年创建、144 位贡献者、★1,170），站内按支持口径归属 ClickHouse、MariaDB、MySQL、PostgreSQL、SQL Server 5 库，类别落在测试/质量。

为什么本期选它：类别轮盘 6/13 转到测试/质量，而它正处在一个罕见的强度期——7 天 618 次提交、90 天 5,143 次，是本周全站测试类项目里维护节奏最猛的一个。基准仓库的提交高峰通常意味着两件事：新引擎/新版本的结果回灌，以及测试脚本对上游变化的适配（这也是基准测试的日常真相——引擎周周变，标尺得跟着量）。对选型者而言，一个「还在被认真维护」的基准，比基准本身更值钱。

适合谁：做 OLAP/分析引擎选型、需要在多个引擎间做性能对比论证的团队；给内部数据库做对外性能叙事的厂商。风险观察点：基准是跑分不是生产——单表分析型负载不代表真实业务混载，别把排名当选型唯一依据；结果页存在版本滞后，引用前先核对引擎版本；许可证未明确标注，商用引用其数据/脚本前要自行确认边界。

3 个月 ★1.5k：dbdelve 用 Rust+GPUI 重做数据库客户端

ShayanAbbas1/dbdelve

原生、跨平台、多引擎的数据库客户端：不装 Electron 不背 JVM，百万行表格滚动不卡；本周 +641 星，是国际阵营里除冷却名单外最猛的增量。

1.5k Star+641 本周37 c/7天5 贡献者
阅读全文 ↓

DBDelve 是一个用 Rust 与 GPUI 编写的原生跨平台数据库客户端：无 Electron、无 JVM，启动瞬时、内存友好，README 直接放了「滚动百万行不卡」的演示视频，主打对Electron 客户端臃肿化的反动。支持 MySQL、PostgreSQL、SQL Server、SQLite 四引擎，站内归类管理；GPL-3.0 许可证，2026-08-17 创建，目前 5 位贡献者，最新版 v0.7.4-nightly.2（11-16）。

为什么本期选它：板块主打国际席位，而它是本周国际增星榜上最鲜活的增量——+641，仅次于两位冷却常客（claude-mem +2,305、dbx +791）与两周前刚写过深读的 codebase-memory-mcp（+317）。3 个月从零到 ★1,495 的斜率，与本刊第 1 期写过的 TablePro、dbx 是同一条曲线——「桌面客户端的原生化回潮」已经是连续四期反复出现的结构性信号，dbdelve 把这个叙事推进到了 GPUI（Zed 编辑器的开源 UI 框架）这一代技术栈上。

适合谁：嫌主流客户端重、日常只做「连库、查表、写 SQL」的工程师与 DBA；在意内存占用与启动速度的笔记本党。风险观察点：版本还在 v0.7.x nightly 阶段，无稳定契约，生产重度依赖要谨慎；引擎支持面窄（4 个），云仓库数仓类接入缺失；单人主导、5 位贡献者，巴士因子低；GPL-3.0 对二次分发有传染约束。

12.3.4 与一则 critical 通告：MariaDB 的一周

MariaDB/server

MySQL 社区分支 11-16 落地 mariadb-12.3.4 维护版；三天前（11-13）刚披露一则 critical——发版与安全修复撞在同一周，升级是本周最实际的动作。

8.6k Star+41 本周13 c/7天83 贡献者
阅读全文 ↓

MariaDB Server 是最著名的 MySQL 社区分支：可插拔存储引擎、窗口函数、向量搜索能力一应俱全，GPL-2.0 许可证，GitHub 仓库 2014 年建立、83 位贡献者、★8,599，站内按兼容口径归属 MariaDB、MySQL、Oracle、SQL Server 4 库，是内核/引擎类别的官方标记项目。

为什么登上事件席：官方发版信号——mariadb-12.3.4 于 11-16 发布，落在本期窗口内；且同一周（11-13）披露了一则 critical 级安全通告，历史在册 28 条。发版落在通告三天之后，两件事大概率有关联，但无论修复是否包含在 12.3.4 内，动作建议都一样：本周内升级。12.3 线的维护节奏本身也是信号——在 12.x 系列迭代期，小版本补丁以月为单位稳定到货，这对「MySQL 兼容生态」的用户是最大的安全感来源。

适合谁：MySQL 生态里想要更强社区主导权的团队、需要 Oracle 兼容层但不想绑死商业许可的技术路线、以及关注向量搜索能力的 OLTP 选型。风险观察点：MariaDB 与 MySQL 的兼容性在边缘处持续漂移，应用迁移要跑兼容测试而不能只看版本号；内核安全通告常态化，把升级纳入例行动作而不是事件驱动；周边生态（驱动/编排）对 MariaDB 的跟进速度普遍慢于 MySQL 官方线。
